# 本地请求与错误报告

六个 Skill 共用同一请求捕获流程。HTTP 请求失败、成功 HTTP 中的无效协议响应、远端任务执行失败，均在第一次观察到时保存 `error-report.md`、`diagnostic.json` 和 `issue-draft.md`。请求上下文另存 `request-context.json`，供下一轮查询复用；正常请求也会保留脱敏后的实际提交证据。生成任务与其模型切换、结果检查共用同一目录和报告。

## 每次向用户反馈

有 `feedback` 时，在首次失败、再次失败、重复查询、恢复成功和最终总结中，逐条转述 `feedback.artifact_links`。每个链接的可见文字都是该文件的**完整绝对路径**，目标必须对应已落盘的真实文件。不要缩写成文件名、`data/...`、相对路径或“同级文件”，也不要放在代码块里。`feedback.user_notice` 已包含可直接使用的 Markdown 链接。旧的 `show_notice` 字段保留兼容，现在每次都有报告时均为 true。

同时说明本次结果、独立错误数、当前任务是否仍在运行，以及下一步。同一失败任务反复查询只更新证据，不增加错误数；每次实际失败的 HTTP 尝试分别计数。恢复成功时交付已有结果，并保留错误报告链接，不能把历史失败说成当前任务仍失败。

`feedback_warning` 或 `feedback.warning` 表示报告/上下文可能没有保存完整；明确说明这一点，保留原任务状态、任务 ID 与已完成文件。只能链接实际存在的文件。报告失败不能触发重发、模型切换或改变原任务结果。

## 证据含义

- `http_status` 只代表**客户端实际收到的 AIHub HTTP 响应**，来源为 `client_response`；没收到或没采集时为 null。异步 `task_status=failed` 可以出现在 HTTP 200/201 等响应里。
- `upstream` 保存 API 实际返回的供应商状态、错误详情、request ID、trace ID、路由、内部重试等字段，并标出 `source`。未暴露的信息一律未知，不能用模型名称猜供应商，也不能把 `service_unavailable` 解释为已证实上游宕机。需进一步定位时，建议管理员按本地报告中的任务/请求 ID 查后台日志。
- 每次 exchange 保存时间、地址、方法、实际请求/响应 JSON、响应头、客户端耗时、超时预算与可观察阶段、尝试序号及既有重试决定。客户端耗时不是供应商内部耗时；没有真实证据的阶段和字段保持 null。
- `original_request` 来自新任务 JSON 的用户原话，与实际提交 prompt/参数分开。旧命令或仅凭 task ID 恢复时缺少原文就显示未知，不能用 Agent 改写的 prompt 回填。
- API Key、Authorization、Cookie、凭证字段与 URL 查询签名脱敏。素材保留资源路径和必要参数信息；二进制、大型 Base64、过长内容明确标注省略。未知业务字段和错误码仍在本地报告中保留。

旧 schema 1 的 `remote_execution.http_status=200` 是旧程序固定填值，不是采集到的 HTTP 证据。读取旧诊断时标注该限制并改为未知；旧报告没有原始请求/响应的部分不能追溯补全。仅解释已有记录，不为补证据重发业务请求。

## 公开反馈

本地报告包含私密提示词、素材定位和原始 ID，不直接用作公开 Issue 正文。`issue-draft.md` 继续只保留公开白名单字段，排除原文、私密链接、路径、定位 ID、凭证指纹及原始响应。向用户提供完整链接供其检查；只有用户明确要求发送时才提交 Issue 或联系管理员。

`AIHUB_ERROR_REPORT_THRESHOLD` 仍可读取旧配置，但不再延迟首错保存和提示。`AIHUB_SUPPORT_URL` 沿用已有服务支持入口；没有配置时只说联系当前服务管理员，不虚构联系方式。报告模块不改变网络重试、模型切换、确认或费用策略。
